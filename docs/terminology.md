# 그루빅 ERP 용어 사전 (Terminology)

화면 간에 **같은 기능은 같은 용어**로 부르기 위한 표준 용어집입니다.
새 UI를 만들거나 라벨을 바꿀 때 이 문서를 먼저 확인하고, 새로운 표준이 정해지면 여기에 추가하세요.

---

## 1. 마진 용어 (3분리: 위험마진 / 마진 단계 / 매출이익율)

원가 개편(2026-06) 이후 마진은 **3곳에서 서로 다른 개념**으로 분리됨. 절대 혼용하지 말 것.

### 1-A. 위험마진 — 원단 원가 계산기 · 원단 리스트 (현행 표준)
순원가에 가산하는 **단일 %**로, '영업 기준원가'를 산출합니다. (메인 전·위험 원단 추가 마진)
- **표준 라벨**: `위험 마진 (%)`
- **필드**: `riskMarginPct` (원단당 1개)
- **공식**: 영업 기준원가 = 순원가 × (1 + 위험마진%)  *(판매마진은 여기서 적용하지 않음 → 견적서 1-C에서)*

| 화면 | 파일 | 형태 |
|-----|------|-----|
| 원가 계산기 | `src/components/cost/CostBreakdownTable.jsx` | 입력(%) |
| 원단 리스트(데스크톱 펼침) | `src/components/fabric/DesktopFabricRow.jsx` | 표시(읽기) |
| 원단 리스트(모바일 카드) | `src/components/fabric/MobileFabricCard.jsx` | 표시(읽기) |

> ⚠️ 원가 계산기·원단 리스트는 더 이상 '마진 단계(1-B)'를 쓰지 않음 — 위험마진으로 대체됨.

### 1-B. 도매(Conv) 마진 단계 지정 — 설계서 전용
판매가(도매가) 산출용 **마진율 단계**. 현재는 **설계서에서만** 사용됩니다.
- **표준 옵션 형식**: `{N}단계 ({M}%)` — 예: `3단계 (19%)`
- **단계 정의(상수)**: [`MARGIN_TIERS`](../src/constants/common.js) — **0~6단계** (10% ~ 28%, 기본 3단계 19%)

| 화면 | 파일 | 형태 |
|-----|------|-----|
| 원단 설계서 / 가설계서 | `src/pages/DesignSheetPage.jsx` | 드롭다운(선택) |
| 설계서 변경 이력 라벨 | `src/components/design-sheet/constants.js` (`FIELD_LABELS`) | 표시(읽기) |

### 1-C. 매출이익율 + 추가 영업마진 — 견적서 · 가설계서
'영업 기준원가'에 적용하는 **판매마진**.
- **일괄 매출이익율(%)**: 전 품목 일괄 적용 + 원단별 개별 수정(`marginRate`)
- **구간별 추가 영업마진**: 구간별 YD당 정액(`marginAdd`), 전체 적용
- **견적서 구간 (2026-10-05)**: 300·500·800·1,000·3,000·5,000YD (키 `300`·`500`·`800`·`1k`·`3k`·`5k`).
  기본 이익율 25/25/23/20/20/20%, 기본 정액 2,000/2,000/1,500/1,000/800/500원 (`constants/quote.js`). 가설계서는 1k/3k/5k 그대로.
  - YD당 정액은 **항상 원화로 적음** (견적 `marginAddCurrency: 'KRW'`, 2026-10-05). 수출 견적은 판매가를 낼 때 견적 환율로 나눠 $로 더함.
    예전 수출 견적은 $로 적혀 있어 그대로 씀.
  - 가설계서(`quoteMarginAdd`)도 원화로 입력·저장하고, 수출 보기에서는 칸 아래에 공통 환율로 환산한 $를 보여 줌.
- **공식**: 판매가 = 영업 기준원가 ÷ (1 − 매출이익율%) + YD당 정액
- **사용 위치**: `src/pages/QuotationPage.jsx`, `src/hooks/domains/useQuotation.js`
- **가설계서 영업견적 시뮬레이션(2026-08 추가, 구간별 개편)**: `quoteMarginRate`·`quoteMarginAdd`를
  **구간별 객체 `{'1k','3k','5k'}`** 로 보유 — 매출이익율·YD당 정액을 1K/3K/5K 각각 개별 입력.
  신규 가설계서 기본값: 이익율 22/20/18%, 정액 0 (**기존 시트·정식 설계서는 불변**).
  `toTierRate`/`toTierAdd`로 정규화(레거시 단일값은 세 구간에 자동 펼침 → 하위호환), 최종 판매가는 `computeSellPrice()`.
  편집화면(`DesignSheetPage.jsx` isTempMode) 시뮬레이션 그리드 + 목록 1K/3K/5K 판매가·마진 범위 배지
  (`TempDesignSheetListPage.jsx`, `useTempDesignSheet.js`). base = `calculateCost().finalCostYd`(영업 기준원가).

> ⚠️ **원가모델 참고**: `calculateCost`의 `priceConverter`/`priceBrand`는 판매가가 아니라 **`finalCostYd`(영업 기준원가) 별칭**이다.
> 설계서 목록도 이 값을 '3K 영업 기준원가'로 표시함 (2026-10-06 — 예전 '도매가·기본단가' 표기는 같은 원가를 판매가처럼 보이게 했음).
> `costInput.marginTier`(도매 마진 단계, 1-B)는 저장·이력추적만 되고 현재 원가계산에는 미사용(판매마진은 견적/1-C로 이관됨).

> ⚠️ 과거 용어(쓰지 말 것): `통합 적용 상수`, `1급~5급`, `마진등급`, `지정 마진율`, `도매 마진`. → 설계서 마진은 `도매(Conv) 마진 단계`, 원단 원가는 `위험마진`, 견적 판매마진은 `매출이익율`로 명확히 구분.

## 2. 가설계서(레시피)와 정식 설계서의 화면 공유

- **가설계서(레시피)** 작성 화면은 **정식 설계서 화면(`DesignSheetPage.jsx`)을 `isTempMode={true}`로 재사용**합니다.
  (진입: `src/pages/TempDesignSheetListPage.jsx` 의 모달)
- 따라서 `DesignSheetPage`의 원사·원가·마진 UI를 수정하면 **정식 설계서와 가설계서 양쪽에 동시에 반영**됩니다.
- 가설계서 전용 차이: 원사 슬롯에 `priceOverride`(단가 직접 입력) 칸이 추가됨. 정식 설계서로 승급(`loadTempToSheet`) 시 `priceOverride`는 폐기되고 원사 라이브러리 단가로 재계산됩니다.
- **양방향 불러오기**: 정식→가설계서(`loadSheetToTemp`)는 목록의 `[설계서 불러오기]`로 등록된 정식 설계서의 스펙·원가를 **새 가설계서로 복제**(원본 불변, 추적 필드 제외, 원사엔 `priceOverride('')` 부여, 마진 기본값 22/20/18%). 가설계서→정식(`loadTempToSheet`)은 그 반대(승급).

## 2-A. 원가 계산 용어 (2026-10 원가 개편 — 상세는 `docs/costing-model.md`)

원가 표(`CostBreakdownTable`)·원가 설정(`CostSettingsModal`)·원단 리스트에서 같은 말로 부를 것.

| 표준 용어 | 뜻 | 필드 / 위치 |
|---|---|---|
| **원가 설정** | 전 품목 공통 원가 기준값 화면 (⚙ 버튼) | `settings/general.costSettings` |
| **편직 난이도** | 품목의 편직 등급 (A/B…) → 정액을 정함 | 품목 `knitGrade`, 설정 `knitGrades` |
| **정액** | 편직비 최저 금액 (오더당). 편직비 = max(정액, 생지 kg × kg단가) | 설정 `knitGrades[].fixedFee` |
| **편직 kg단가** | 품목별 편직료 (원/kg, 생지 기준) | 품목 `knitKgRate` |
| **kg단가 구간** | 품목별 'N kg 이상 → 단가' (선택) | 품목 `knitKgRateTiers` |
| **가공 유형** | 일반·스판물·기모물… → 가공 LOSS를 정함 | 품목 `processType`, 설정 `processTypes` |
| **가공 LOSS** | 염가공·후가공에서 줄어드는 비율 (생지 → 가공지) | 설정 `processTypes[].lossPct` |
| **편직 LOSS** | 편직에서 줄어드는 비율 (원사 → 생지), 생지 kg 구간별 | 설정 `knitLossBrackets` |
| **가공지 kg / 생지 kg / 원사 투입 kg** | 완성 원단 무게 / 편직 후 원단 무게 / 들어가는 원사 무게 | 원가 표 ③ 구간별 산출 |
| **이화학검사** | 컬러수 × 1컬러당 검사비 (오더당) ÷ 수량 | 설정 `chemTest` |
| **운임** | 수량 구간별 오더당 금액 ÷ 수량 | 설정 `freightBrackets` |
| **외관검사** | 전 품목 공통 YD당 단가 | 설정 `visualInspectionPerYd` |
| **품목별 추가비용** | 품목마다 따로 넣는 YD당 비용 (선택) | 품목 `etcCosts[{name, perYd}]` |
| **운반비** (원사) | 원사 kg당 운반비. 국내 업체는 공급처마다 고정 원/kg | 원사 공급처 `freight` |
| **수입 / 수입사** | 원사 공급처 줄의 [수입] 체크 → 운반비를 수입 국가 kg 구간으로 | 원사 공급처 `isImport` |
| **수입 국가** | 수입 원사 운반비 구간을 고르는 나라 (기본 중국) | 원사 공급처 `importCountry`, 설정 `importCountries` |
| **수입 원사 운반비** | 그 원사 kg(원사 투입 kg × 혼용률) 구간의 원/kg ('N kg 미만' 구간). 재료비에 포함 | 설정 `importCountries[].brackets` |
| **2컬러 기준** | 원가 표 소량 구간(300·500·800YD) — 2컬러로 나눠 염색한다고 봄 (이화학도 2컬러) | `COST_DISPLAY_TIERS` group `small` |
| **MCQ 충족 기준** | 원가 표 1,000·3,000·5,000YD — 컬러마다 MCQ를 맞췄다고 봄 → 염색 최소 청구 없음 | `COST_DISPLAY_TIERS` group `mcq` |
| **염가공료** | 염색·가공 공임 (원/kg, **생지 kg** 기준 — 2026-10-03부터) | 품목 `dyeingFee` |
| **염색 최소 청구** | 한 컬러를 이 kg(**생지**)보다 적게 염색해도 이 kg로 청구 (기본 100kg) | 설정 `dyeMinKgPerColor` |
| **원가 확인 필요** | 원가가 덜 잡히거나 틀릴 수 있다는 경고 (혼용률 ≠ 100% · 원사 미선택 칸 · 라이브러리에 없는 원사 · 단가 0원 원사 · 중량 0). 목록·견적에서는 짧게 **'원가 확인'** 배지 | `calculateCostTiers().costWarnings`, `CostWarnings.jsx` |

> ⚠️ 쓰지 말 것: `1K/3K/5K 편직료`, `구간별 편직 Loss`, `염색 LOSS`(→ **가공 LOSS**), `기타비용(외관/이화학/운임)`(→ 원가 설정의 각 항목).
> ⚠️ 쓰지 말 것: `미등록 원사 포함 (임시 데이터)`·`혼용률 오류` 같은 따로 노는 경고 → 모두 **원가 확인 필요**로 묶어서 사유를 나열.
> ⚠️ **운임 ≠ 운반비**: 운임은 원단 오더 납품 운임(수량 YD 구간, 오더 총액), 운반비는 원사 kg당 운반비(국내 고정 / 수입 국가 kg 구간). 섞어 쓰지 말 것.
> 원가 표의 6구간(300·500·800YD 2컬러 기준 + 1,000·3,000·5,000YD MCQ 충족 기준)은 '입력 칸'이 아니라
> **수량을 넣어 계산한 결과**를 보여주는 열이다. 견적서·원단 목록·가설계서 판매가는 1K/3K/5K만 쓴다.

## 2-B. 환율 용어 (2026-10-03, 내수·수출 두 칸 2026-10-07 — 상세는 `docs/costing-model.md` §5·§5-A)

| 표준 용어 | 뜻 | 필드 / 위치 |
|---|---|---|
| **공통 환율** | 회사 전체가 같이 쓰는 환율 (화면 위 환율 칸, 바꾸면 전 직원에게 적용) — **내수 환율·수출 환율 두 칸**을 함께 부르는 말 | 코드 `exchangeRates = { domestic, export }` |
| **내수 환율** | 달러로 사는 원사 → 원화 (내수 원가·원사 라이브러리 내수 단가·내수 견적) | `settings/general.exchangeRate` (예전 공통 환율 칸) |
| **수출 환율** | 원화 원가 → 달러 (수출 원가·수출 견적·수출 보기의 '≈ $'). 아직 따로 저장 전이면 내수 환율과 같은 값 | `settings/general.exportExchangeRate` |
| **실시간 환율** | 환율 칸 옆 참고용 시장 환율 (보기만 — 내수·수출 환율은 직접 입력) | `hooks/useMarketRate.js` |
| **견적 환율** | 그 견적을 계산한 환율 (견적서 Rate 칸) = 그 견적 시장의 공통 환율. 공통 환율이 바뀌어도 그대로 | 견적 `exchangeRate` |
| **현재 원가로 다시 계산** | 견적 품목 기준원가를 지금 원가 + 그 시장의 지금 공통 환율로 다시 계산하는 버튼 (매출이익율·YD당 정액은 그대로) | `useQuotation.handleRecalcQuote` |

> ⚠️ 화면 라벨에 `전역 환율`·`기준 환율`·`글로벌 환율` 쓰지 말 것 → **공통 환율**(두 칸을 함께 말할 때) / **내수 환율**·**수출 환율**(한 칸).
> 견적서 안에서는 **견적 환율**(Rate 칸)과 구분. 화면 문구는 `helpers.rateLabel(시장)`으로 '내수 환율'/'수출 환율'을 맞춤.

## 2-C. 견적서 용어 (2026-10-05 — 상세는 `docs/costing-model.md` §5-B)

| 표준 용어 | 뜻 | 필드 / 위치 |
|---|---|---|
| **기준 견적** | 정해 둔 수량 구간(300~5,000YD)별 단가표. 바이어에게 **기준 견적서**로 보냄 | 견적 `items`, 출력 kind `standard` |
| **별도 견적** | 수량·컬러수·제외 항목을 바꿔 원가부터 다시 계산한 단가. 바이어에게 **별도 견적서**로 따로 보냄 | 견적 `customItems`, 출력 kind `special` |
| **견적서 표시** | 바이어 견적서에 나갈 구간(기준) / 줄(별도) 체크 | `shownTiers` / `row.show` |
| **외관검사 제외 · 시험성적서 제외** | 그 비용을 기준원가에서 뺌 (시험성적서 = 이화학검사). 칸마다 전체에 적용하는 버튼 ('기준 견적 전체' / '별도 견적 전체') | `excludeVisual`·`excludeChem` / `customExcludeVisual`·`customExcludeChem` |
| **원단 검색·추가** | 두 칸 공통 원단 추가 버튼 (팝업에서 그 칸에 이미 있는 원단은 '추가됨'). 표 아래 Article 입력·엑셀 세로 복붙도 같음 | QuotationPage `AddFromListButton` · `ArticleQuickAdd` |
| **별도 견적으로 복사** | 기준 견적에서 체크한 원단을 별도 견적 줄로 (300YD · 2컬러로 시작) | 기준 견적 도구줄 버튼 |

## 3. 저장 규약 (데이터 유실 방지)

- 폼 저장 핸들러는 `saveDocToCloud(...)`(App.jsx)를 **`await`** 하고, **성공(`true`)했을 때만** 폼 리셋·성공 토스트·모달 닫기를 수행합니다. 실패 시 입력값을 보존하고 에러를 표면화합니다.
- `src/services/db.js`의 `saveDocument`는 저장 전 **undefined 필드를 제거**합니다. (Firestore는 `undefined` 필드를 거부하므로, 일부 필드가 비어도 문서 전체 저장이 실패하지 않도록 함)
- 원사가 들어가는 폼(원단·설계서·가설계서·아이템화·원단 엑셀 등록)은 **원사 혼용률 합계가 100%가 아니면 저장하지 않습니다**
  (`isYarnRatioComplete` — 소수 둘째 자리 반올림 후 100). 새 폼 기본값은 첫 칸 100%라 원사를 고르기 전 초안도 저장됩니다. (2026-10-03, 상세 `docs/costing-model.md` §4-B)
- 개발 의뢰·메인 디테일 저장도 서버 저장을 기다렸다가 성공했을 때만 폼 비우기·성공 알림 (2026-10-06 — 예전엔 기다리지 않았음).
- **문서를 통째로 덮어쓰는 저장**(`saveDocument` = setDoc)이라, 폼에 없는 칸이 있는 문서는 **기존 문서를 먼저 깔고 폼 값을 얹어** 저장합니다.
  예) 개발 의뢰 수정 저장 — 원가 견적(`costQuote`)·Drop 사유가 수정할 때마다 지워지지 않게 (2026-10-06).
- **삭제**도 같은 원칙: `deleteDocFromCloud(...)`가 `true`일 때만 연결 정리(설계서↔원단↔개발 의뢰)·목록에서 빼기·성공 알림을 합니다.
  실패하면 `false`를 돌려주고 '삭제 실패' 알림은 그쪽에서 띄움 (오류로 멈추지 않음). 편집 창의 삭제 버튼은 지워졌을 때만 창을 닫습니다. (2026-10-06)
- **설계서 삭제** (`useDesignSheet.handleDeleteSheet` — 설계서 창 [삭제]·개발/설계 현황 목록 🗑 공통, 2026-10-06):
  아이템화 완료는 막음, 샘플 진행 중은 한 번 더 경고, 확인 창에 어떤 설계서인지(EZ-TEX No.·개발번호·원단명)와 같이 풀리는 연결을 적음.
  연결된 개발 의뢰는 남고 연결만 풀림(개발 의뢰 현황에 '설계 대기'로 다시 보임). **연결된 원단도 남기고 원단의 `linkedSheetId`만 비움**
  (대표님 결정 — 예전엔 원단 쪽 연결이 남아 그 원단을 다른 설계서에 다시 연결할 수 없었음).
  생산 현황 **샘플 오더도 남기고 오더의 `linkedSheetId`만 비움** (2026-10-10).
- **설계서 Drop**: 설계서를 먼저 Drop으로 저장하고, 저장됐을 때만 개발 의뢰 연결을 풂. 생산 현황 샘플 오더는 **'Drop'**으로 닫힘
  (완료 + `dropInfo` — 복원하면 Drop 전 상태로, 2026-10-10).
- **개발 의뢰 Drop (설계서가 있는 의뢰)**: 설계서도 같이 Drop (대표님 결정 2026-10-10) — `App.dropDevWithSheet`: 설계서를 먼저(확인 창 없이), 그다음 의뢰(사유 저장 + `droppedSheetId`).
  **생산 현황에서 샘플을 Drop해도 같음** — 의뢰가 있는 설계서면 같은 Drop 사유 창 → 의뢰·설계서·샘플 오더 같이 (자체개발은 설계서만).
  보관함 'Drop된 의뢰' [복원]: 같이 Drop된 설계서가 있으면 설계서까지 복원(의뢰 '개발 확정', 샘플 오더 Drop 전 상태), 없으면 '의뢰 접수'로.
  의뢰가 그사이 다른 설계서로 진행 중이면 옛 설계서 복원은 막음 (한 의뢰에 설계서 둘 방지).
  개발 의뢰 현황 줄의 🗑 는 설계서가 있으면 **설계서만** 삭제 (의뢰는 '개발 확정' 줄로 남음).
- **Drop된 설계서**는 열어서 고쳐 저장해도 의뢰를 되살리지 않음(`linkAndConfirm`이 Drop 의뢰는 건드리지 않음). 단계 이동·원단 등록·EZ-TEX 등록은 복원한 뒤에만 (2026-10-10).
- **샘플 오더 보호** (2026-10-10): 설계서와 연결된 샘플 오더는 메인으로 못 바꿈 · order#를 고치면 설계서 EZ-TEX O/D NO.도 같이(설계서 변경 이력) ·
  설계서 EZ-TEX 칸에 기존 메인 오더 번호를 넣으면 막음 · 샘플 오더가 있으면 설계서 EZ-TEX 번호를 비울 수 없음 · 오더 삭제 확인 창에 설계서가 어떻게 되는지 안내.
- **설계서 창을 열어 둔 사이** 다른 곳(다른 PC)에서 바뀐 EZ-TEX 번호·의뢰 연결·원단 연결은 이 창에서 손대지 않았으면 저장소 값 유지 (`useDesignSheet` `LINK_KEYS`, 2026-10-10).
- 목록의 **Drop / 삭제** 구분은 개발 의뢰·설계서 모두 같음: Drop = 보관함으로(복원 가능), 🗑 삭제 = 영구 삭제(복구 불가).
- **개발 의뢰 삭제**: Drop된 설계서가 그 의뢰를 가리키면 지운 뒤 설계서의 의뢰 연결을 풂(개발번호 글자는 남김). 개발번호는 다시 쓰지 않음 —
  새 번호는 의뢰·설계서·견적서에 쓰인 번호 중 가장 큰 번호 + 1 (2026-10-06, 상세 `docs/costing-model.md` §5-C).
- **단계 변경**(개발 의뢰 드롭다운·다음 단계·복원)도 저장이 끝나고 성공했을 때만 '변경되었습니다' (2026-10-06).
- **날짜만 저장하는 칸**(견적일·PI·랩딥·개발 의뢰일·설계서 등록일·원사 단가 이력)은 `helpers.todayLocalISO()` — 이 PC 시간 기준 'YYYY-MM-DD'.
  `toISOString()`은 UTC라 한국 시간 오전 9시 전에는 어제 날짜가 됨 (2026-10-06). 시각까지 남기는 updatedAt 등은 그대로 ISO.
- 설계서의 **'원단 리스트에 등록'**은 설계서를 먼저 저장하고, 저장에 성공하면 **그 저장본으로** 원단을 등록한 뒤 연결합니다.
  원단 저장이 실패하면 설계서를 '없는 원단'에 연결하지 않고 창을 그대로 둡니다. (`useDesignSheet.saveSheetAndRegisterFabric`, 2026-10-06)

## 4. 팝업 창 규약

- 팝업 뒤 어두운 배경은 **`src/components/common/ModalBackdrop.jsx`**를 씁니다 — 배경을 **눌렀다가 배경에서 뗐을 때만** `onClose`.
  입력칸에서 글자를 드래그해 선택하다가 창 밖에서 마우스를 떼도 닫히지 않습니다 (그냥 `onClick`이면 브라우저가 이를 '배경 클릭'으로 보내 창이 닫힘,
  대표님 제보 2026-10-06 '아이템 수정 중'). 새 팝업도 `<ModalBackdrop className="fixed inset-0 …" onClose={닫기}>`로 만듭니다.
- 입력하는 팝업은 고친 내용이 있으면 닫기 전에 '변경사항이 있습니다 — 저장하고 나가기 / 저장 안 함 / 계속 편집'을 묻습니다:
  원단 편집·견적서, 그리고 2026-10-06부터 **가설계서 편집·설계서 작성(정식)·개발 의뢰 작성·메인 디테일 작성·원가 견적** (대표님 결정). 원가 설정은 '닫을까요?' 확인.
- **팝업은 화면의 `space-y-*`(세로 간격) 칸 밖에 둡니다.** 안에 두면 팝업(`fixed`)에도 위 여백이 붙어 창이 아래로 밀리고
  맨 위 띠가 어둡게 안 덮입니다. 개발/설계 현황은 팝업들을 페이지 칸 아래 따로 모아 둠 (2026-10-06 — 의뢰 등록·저장할까요?·의뢰 연결·원가 견적·Drop·보관함 창).
- Drop 사유 창처럼 **고르는 칸만 있는 작은 창**도 고른 값이 있으면 닫기 전에 묻습니다 ('저장하고 나가기' = 그 처리 실행).
- 저장·처리 버튼은 **처리 중 잠금**을 `useRef`로 겁니다 (화면 상태(useState)는 늦게 바뀌어 빠른 두 번 누름을 못 막음 — 견적서 저장 `savingRef`와 같은 방식).
  - 새 팝업은 `hooks/useUnsavedGuard.js`(열릴 때 값과 비교, `isDirty`·`rebase`) + `components/common/UnsavedChangesDialog.jsx`(확인창)로 만듭니다.
  - **새 문서는 빈 양식 기준** — 불러오기·의뢰에서 채운 내용도 저장 전이면 묻습니다. `id`·`createdAt`·`updatedAt`은 비교에서 뺌.
  - 설계서는 단계·연결·상태·이력처럼 **누르는 즉시 저장되는 칸**을 비교에서 뺌 (단계만 바꾸고 닫으면 묻지 않음).
  - 메인 디테일 '연속 작성' 저장 뒤 남겨 둔 Order/Article은 저장 안 한 변경이 아님 (`rebase`).
